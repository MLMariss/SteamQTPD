## Axis 2 — Refresh schedule (is the pipeline keeping up?)

Covered rows split by how each row's **own scraper** will treat it on the next pass — NOT against a flat target. The **7d (active)** lane is games updated within 90d (short cooldown); the **30d (dormant)** lane is everyone else (long cooldown, refreshed rarely *by design*). Track totals **include** their overdue members. **overdue** = already past its lane's cooldown = real backlog. **never** = no data yet = fill frontier. **empty** = correctly skipped (below the row's own review floor / null score), not pending work.

### Playtime raw — surface refresh (`playtime_raw/`)

Staleness is the **real per-game `scraped_at`**, measured against the real ladder (release-age tiers <7d→1d · <30d→3d · <90d→7d · else 30d; halved above 1,000 reviews, then floored by the popularity tiers >1000→5d/>500→10d). Because the cooldown varies per game, **promise** is the range actually applied within each release-age tier. `covered` 93,141 · `overdue` 30,884 · `never` 4,309 · `empty` 31,995.

| Release age | n | Promise | Median stale | p90 | Inside window |
|---|---:|---:|---:|---:|---:|
| 0–7 d | 228 | 0.5–1 d | 1.7 d | 4.6 d | 39.0% |
| 7–30 d | 1,115 | 1.5–3 d | 4.4 d | 9.0 d | 39.9% |
| 30–90 d | 2,860 | 3.5–7 d | 4.8 d | 12.3 d | 64.4% |
| 90 d+ | 88,938 | 5–30 d | 6.0 d | 37.0 d | 67.3% |

**A surface refresh is not a full one.** For a game already holding 3,000 reviews a normal visit stops after page 1, so only its newest ~100 playtimes are re-read; positions below that stay frozen at whatever they were when first captured. Small games (below their rung) are walked to the end of Steam's list every visit, so for them this table *is* the whole story.

Files with a single-window (not two-track) refresh rule:

- **`games.json` core** (`scraper.py`): fresh 26,043 · overdue 515 · never 0 · last-modified-only 102,887. Games within 365d of release are on the age-tiered review refresh (≤3d→0.25d, ≤10d→0.5d, ≤30d→1d, ≤60d→2d, ≤90d→3.5d, ≤180d→7d, ≤365d→15d), so fresh/overdue are exact for them. Older games refresh on Steam's `last_modified` (invisible locally) plus the PICS review-drift trigger, and are counted separately rather than scored against a cooldown they don't have.
- **`hltb.json`** (`hltb_refresh.py`): fresh 34,237 · overdue 1 · blank-frozen 95,092 · blank-active 102. Windows: partial 14d, full 365d; blanks back off 3→30→180d by attempt count.
- **`prices.json`** (`price_and_sale.py`): no cooldown gate — the whole non-free base is re-batched every 3h, so there is no meaningful staleness backlog to bucket.
- **`tags.json`** (`tags_refresh.py`): **no timestamp stored and no rescrape schedule** — coverage-only. See Future work below.
- **`playtime.json` / `ratings.json`**: derived from `playtime_raw/` on every raw pass; staleness inherits from the raw shard row above.
- **`pics_raw/`** (`pics_refresh.py`): fresh 128,960 · overdue 386 · never 99. Single flat `--stale-days 14` window (daily cron), and — unlike playtime — keyed on a **real per-game `_ts` fetch stamp**, so overdue here is exact, not a proxy. `never` = catalog games not yet in `pics_raw/` (the fill frontier). `pics/` is derived from `pics_raw/` by `pics_summarize.py` on every pass, so its staleness inherits from this row.

## Notes

**Prices.** `prices.json` holds **110,716 rows (85.5% of catalog)**, tracking the non-free base (**110,736** games after removing 18,709 `is_free`). **10,588 of 110,716 priced titles (9.6%) are currently discounted**; sale end-dates come from the `IStoreBrowseService/GetItems` pass.

**Playtime backfill.** Raw playtime covers **93,154 games (72.0% of catalog)**. The honest denominator is the addressable set after the `MIN_REVIEWS_FLOOR = 5` gate — **97,450 games (75.3% of catalog)** — against which raw is **95.6% of addressable**. The other **31,995 games are below the floor and correctly skipped** (too few reviews to produce a sentiment-split median).

**Summarizers run on every raw pass.** Raw 93,154 · summarized 92,719 · rated 92,696 (current gap 435). `playtime_summarize.py` and `ratings_summarize.py` are chained into `playtime-raw.yml`, so the small frontend files refresh right after the shards do (8×/day). Any residual gap is just within-run ordering between the shard commit and the summarize steps, not a stalled pipeline.

**Update events.** `updates.json` (event_type-based patch history) covers **53,368 games (41.2%)**, built from **64 of 64 `updates_raw/` shards populated**. This layer feeds the frontend's **Updated column cadence badge** (`N · 90d` / `N · 1y`, from the summed 90d/365d `counts`) and backfills a null News-API `last_update_ts`. It is gated by its own 10-review floor (playtime's is 5; the two no longer match). As the remaining shards populate this coverage rises; the precedence flip (event layer becomes primary over News-API) is gated on that coverage — see ARCHITECTURE §9.5 / §3.1.

**HLTB estimates refresh live.** **19,037 of 129,432 `hltb.json` entries carry the `est` flag** (14.7%), leaving **110,395 reals (85.3%)**. `hltb_estimate.py` is a shared helper imported by `hltb_refresh.py` (as `HE`) and called in the fill loop, so estimates recompute from live median ratios every 2h as new reals land — not a stale one-off.

**Rating % / review count.** Rating % is present for **117,520 games (90.8%)**; review count for **121,045 (93.5%)**. The gap is titles with too few reviews to carry a meaningful score.

**Tags** are non-empty for **129,396 games (100.0%)**. The remainder are untagged on SteamSpy (typically very-low-review or unreleased titles).

## Future work

- **Tag refresh schedule.** `tags.json` currently has no per-entry timestamp and no rescrape cadence — tags are fetched once and left. Tags do drift (Steam user-tag votes shift, new tags get added), so a light periodic re-check (e.g. weekly/monthly, oldest-first, small budget) is worth adding. That needs a per-entry `scraped_at` in `tags.json` first, after which tags can join Axis 2 as a proper row here.
- **Uniform-refresh review.** Once the fill frontier drains (near-100% coverage), revisit whether the dormant 30–45d cooldowns should tighten toward a flatter, faster whole-catalog refresh. Today's split (active 4–7d / dormant 30–45d) deliberately front-loads budget onto games whose data actually moves; a uniform target only makes sense once no backlog is competing for that budget.
